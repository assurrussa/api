# Процессный E2E

`make e2e` проверяет цепочку административный CLI → PostgreSQL → HTTP,
включая два независимых серверных процесса. `make check` включает этот запуск
после unit/integration/race-тестов и consumer probe.

```sh
make e2e
# Выбрать одну группу, сохранив изоляцию и очистку стенда:
bash scripts/e2e.sh -run 'TestEndToEnd/database_outage_and_recovery'
```

Стенд сам задаёт `API_E2E_DATABASE_URL`, `API_E2E_CONTAINER` и
`API_E2E_RUN_ID`. Не задавайте их вручную: перед инъекцией неисправностей
тест сверяет уникальную метку контейнера с идентификатором запуска. Прямой
`go test -tags=e2e ./e2e` без скрипта завершается ошибкой. Существующие БД и
демо-окружение не используются. Нужны Go 1.27, Bash и Docker; серверный
процесс проверяется на корректное завершение через interrupt.

| Группа | Наблюдаемое поведение |
| --- | --- |
| Выдача и HTTP | CLI возвращает секрет один раз; HTTP 200 содержит правильный Principal без токена |
| Граница HTTP | Нет токена, неверный секрет/ID, два Authorization, лишние пробелы, большой заголовок, токен только в query/cookie/body → 401 с challenge |
| Scopes | Доступ без `orders:read` → 403; снижение и восстановление scopes клиента отражаются на действующем токене |
| Отказы выдачи | Неизвестный scope, превышение прав клиента, отрицательный и чрезмерный TTL отклоняются без создания Credential |
| Бан | Все токены клиента → 401; выдача и ротация запрещены; разбан возвращает только неотозванные доступы |
| Ротация | Постоянный Credential ID, новое поколение и секрет; grace=0 отключает предыдущую текущую версию |
| Переходный период | Обе версии работают в grace; следующая ротация не продлевает старый переход; большой grace не продлевает исходный TTL |
| Истечение | Токен истекает при ещё свежем кэше; администратор может обновить неотозванный истёкший доступ |
| Отзыв | Все версии Credential получают 401; ротация отозванного доступа запрещена; бан/разбан не восстанавливает его |
| RevokeAll | Отозваны все существующие Credential и переходные версии; новый доступ после операции разрешён |
| Гонка ротаций | Два CLI с одинаковым ожидаемым поколением: один успех и один conflict; токен победителя работает |
| Метаданные | Keyset-пагинация клиентов и доступов; ответы не раскрывают токены и digest |
| Изоляция | Токен из одной схемы не авторизует запрос к серверу другой схемы |
| Потерянное событие | Изменение в primary без NOTIFY всё равно прекращает доступ в пределах бюджета свежести |
| Переподключение LISTEN | Завершён только backend тестового listener; после переподключения отзыв снова применяется |
| Отказ БД | Strict → 503; кэши могут разрешать свежие записи, но после MaxStaleness → 503; неизвестный токен не авторизуется |
| Восстановление | После старта той же БД HTTP-процессы возвращаются к 200; последующий бан снова даёт 401 |
| Начальная загрузка | RCU при недоступной БД завершается с ошибкой до открытия HTTP-listener |
| Завершение | HTTP-процессы выходят без ошибки и сообщений race detector; stdout/stderr не содержат выданных токенов |

В группах strict/ARC/RCU изменения выполняются отдельными CLI-процессами.
Ожидание уведомлений ограничено четырьмя секундами при периоде RCU 30 секунд
и MaxStaleness в минуту: истечение кэша не подменяет проверку доставки
инвалидации. В тестах потери события и отказа БД MaxStaleness — две секунды,
период RCU — 500 мс. Потеря события моделируется прямым SQL UPDATE без
NOTIFY исключительно в тестовой схеме; обычные записи должны идти через
Store/Service. Опрос HTTP имеет запас для транспорта и планировщика;
точные временные границы отдельно проверены unit-тестами с управляемыми часами.

Это функциональная проверка текущего checkout и процесса примера. Она не
проверяет опубликованную версию, `goadmin`, TLS/reverse proxy, повреждение БД,
сетевые разделения с зависшими соединениями или предел устойчивой нагрузки.
Свежий кэш во время отказа БД вправе отвечать 200 либо 503 при промахе;
обязательный критерий — отсутствие разрешения по просроченному состоянию.
